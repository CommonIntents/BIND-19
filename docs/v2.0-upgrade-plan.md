## 二、核心设计原则（哲学驱动）

本协议的设计受以下六条 DNA 哲学指导，每条原则都在协议结构中有显式对应：

| 哲学 | 含义（在此协议中） | v2.0 中的具体体现 |
|---|---|---|
| **按需加载** | 只加载当前决策所需的模块，不预先计算未使用的安全度量 | PAH 第一层（64-bit）在接收帧后立即验证（必要安全机制，不可跳过）；第二层（512-bit）仅在载荷解密后异步验证。不验证就不加载签名逻辑——但必要安全机制必须加载 |
| **按需驱动** | 事件驱动，无轮询。无事件时零能耗，不主动检查 | CATASTROPHIC 检测使用硬件中断或 `tokio::sync::Notify`，禁止任何形式的 `loop + sleep` 轮询 |
| **极致复用** | 不重新发明轮子，复用经过工业验证的成熟组件 | 复用 SHA-256、AES-GCM、Ed25519、BIND-19 传输层；PAL 不推翻旧四层结构，仅插入新层 |
| **物理事实优先** | 安全决策基于物理传感器读数，而非 AI 语义推理或网络信任 | PAL 头部字段（Modality/Stance/Edge/Risk-Level）由传感器驱动生成；PAH 由传感器数据哈希锁定，AI 无权修改 |
| **确定性优先** | 固定路径、固定偏移、固定算法，无分支决策，行为可预测 | PAL 24 字节固定偏移；加密路径固定（AES-GCM）；哈希截断固定（SHA-256/MSB 64-bit）；Seq-Counter 单调递增；无 if-else 决策树 |
| **极致节能** | 固定计算路径利用硬件流水线；明文元数据不解密；最小头部开销 | Tuck 只读取 PAL 头部（24 字节明文），不解密载荷；24 字节 = 3×64-bit 对齐 SIMD；固定加密路径无分支 |

## 三、升级理由

CI-144 v1.0 缺少"特征"——可被 Tuck 等闸门硬实时读取的、固定偏移的、明文可见的物理安全元数据。

| 缺失的特征 | 后果 |
|---|---|
| 无物理上下文（姿态/临边/模态） | Tuck 无法判断"AI 在做什么类型的动作" |
| 无风险等级 | Tuck 无法判断"这个动作有多危险" |
| 无硬覆盖标识 | 灾难场景下无法无条件放行，可能被策略误拦截 |
| 无可观测的固定偏移头部 | Tuck 必须解密载荷才能做决策，违背"极致节能" |
| 无防篡改的物理上下文哈希 | AI 可能伪造物理上下文，绕过安全拦截 |

**一句话总结**：v1.0 定义了"AI 之间怎么说"，v2.0 补齐"AI 在物理世界中怎么做"。

## 四、新增层级：物理锚定层（Physical Anchor Layer, PAL）

插入位置：`INTENT-7 → **PAL** → CAPABILITY-13 → BIND-19 → SECURE`

**PAL 总长度固定为 24 字节（192 bits）**，全部明文、固定偏移，即使整个帧被加密，PAL 也在传输层可见。

### PAL 固定头部定义（24 字节 / 192 bits）

| 位偏移 | 长度(bit) | 字段名 | 枚举值 / 说明 |
|---|---|---|---|
| 0-1 | 2 | `Modality` | 0=COGNITIVE, 1=RENDER, 2=EXECUTIVE, 3=SENSOR_FEED |
| 2-3 | 2 | `Risk-Level` | 0=LOW, 1=MEDIUM, 2=CRITICAL, 3=CATASTROPHIC |
| 4-5 | 2 | `Body-Stance` | 0=SEATED, 1=STANDING, 2=MOVING, 3=UNKNOWN |
| 6-7 | 2 | `Proximity-Edge` | 0=SAFE, 1=WARNING, 2=DANGER, 3=CRITICAL_EDGE |
| 8 | 1 | `Output-Dest` | 0=INTERNAL, 1=EXTERNAL |
| 9 | 1 | `Override-Flag` | 0=NORMAL, 1=HARD_OVERRIDE |
| 10-13 | 4 | `PAL-Version` | v2.0 = 0001（支持 16 个版本） |
| 14 | 1 | `Replay-Enable` | 1=强制检查 Seq-Counter；0=降级（见规则 6） |
| 15 | 1 | `Reserved` | 强制为 0（未来扩展走 RFC/ADR 流程） |
| 16-127 | 112 | `Physical-Context-Hash` | SHA-256 截断（高 112 位） |
| 128-191 | 64 | `PAH-Signature` | ECC 签名截断（快速校验层，算法见规则 5） |

## 五、BIND-19 帧结构升级

新帧结构：
```
[ 8 字节 BIND-19 传输头 ] + [ 24 字节 PAL ] + [ 可变长加密载荷 ]
```

**BIND-19 传输头新增字段（强制）**：

- **`PAL-Present`（1 bit）**：v2.0 帧置 1，v1.0 接收端忽略（向后兼容）。v2.0 接收端若收到 PAL-Present=0，按 v1.0 旧逻辑处理。
- **`Seq-Counter`（16 bits）**：单调递增序列号（防重放）。
  - 位置：复用原 BIND-19 v1.0 头部的第 6-7 字节（原 Reserved 区域）。
  - 初始化：每次冷启动时取随机值，避免重启后序列号重置被攻击者利用。
  - 原子递增：多线程环境使用 `AtomicU16` + `fetch_add(1, Ordering::SeqCst)`，确保严格单调递增。
  - **回绕策略**：Seq-Counter 从 65535 回绕到 0 时，强制触发密钥轮换（见规则 7）。
  - **32-bit 扩展**：当前设计为 16-bit。32-bit 扩展方案（含帧结构扩展、向后兼容评估）详见 ADR-0009（Alpha 期间评估，不阻塞当前设计冻结）。

## 六、核心规则（协议宪章）

### 规则 1：CATASTROPHIC 硬覆盖

```
IF PAL.Risk-Level == 3 (CATASTROPHIC) AND PAL.Override-Flag == 1
THEN 接收端必须：
  1. 物理层优先响应（事件驱动，禁止轮询）
  2. 并行通过任何可用通道向人类发送紧急信号
  3. 该帧优先级高于任何本地策略缓存、用户配置或 AI 调度
```

### 规则 2：CATASTROPHIC 审计

每次 CATASTROPHIC 硬覆盖触发时，必须生成不可篡改的审计日志，记录触发时间、PAL 内容、传感器上下文、BIND-19 序列号。

### 规则 3：不可协商性

CATASTROPHIC 硬覆盖规则是协议的不可协商部分（Non-Negotiable Section）。任何声称"兼容 CI-144"的实现，若违反此规则，即自动丧失兼容性声明资格。**调试模式（CI144_DEBUG=1）下规则 1-3 仍然生效，不可绕过。**

### 规则 4：向后兼容与版本治理

- **向后兼容**：v2.0 发送端必须在 BIND-19 头中置 PAL-Present=1。v1.0 接收端忽略该标志及后续字节，仍可处理载荷（但无法利用 PAL）。v2.0 接收端若收到 PAL-Present=0，视为 v1.0 遗留帧，按旧逻辑处理。
- **Reserved 治理**：PAL 第 15 位目前强制为 0。未来任何使用该位的扩展，必须提交正式 ADR 并经协议委员会审查分配。接收端若发现 Reserved 位非零，应触发协议版本协商流程，不得静默忽略。
- **PAL-Version**：当前 v2.0 = 0001。接收端若收到不支持的 PAL-Version，拒绝帧并按版本协商流程处理。

### 规则 5：PAH 强制验证（双层安全架构）

**第一层（快速校验层，Tuck 硬实时，必须实现）**：

- Tuck 必须在决策前验证 `PAH-Signature`（64-bit ECC 截断）。
- **截断算法**：64-bit PAH-Signature = 完整 ECC 签名（如 Ed25519 的 512-bit）的 SHA-256 哈希值前 64 位（MSB）。此算法固定，跨实现必须一致。
- **验证失败**：立即拒绝帧 + 拉高 ERROR 电平 + 声光告警 + 写入审计 `PAH_FAIL`。
- **软件实现**：使用 ed25519 软件库实现。Tuck（独立进程，硬实时路径）直接在当前线程验证（10-50μs 可接受）；Helix-Mind/Anaphase（异步事件循环）使用 `tokio::spawn_blocking` 避免阻塞事件循环。验证延迟不得超过 100μs。
- **硬件阶段**：替换为 ASIC/FPGA 加速 ECC 验证，接口不变。

**第二层（完整验证层，载荷解密后，异步追责）**：

- 所有具身帧在 INTENT-7 载荷头部必须附带完整的 512-bit ECC 签名（如 Ed25519 全量签名）。
- **位置**：INTENT-7 v2.0 载荷头部扩展区，格式为 `[512-bit Sig] + [Varint Payload-Len] + [Payload]`（详见 ADR-0001）。
- **验证逻辑（致命边界条件）**：
  - 若第一层 64-bit 验证失败 → 直接拒绝帧（按规则 5 第一层处理，不可动摇）。
  - 若第一层通过、但第二层 512-bit 验证失败 → 不拒绝帧（避免实时阻塞），触发异步告警，标记该会话为"可疑"，连续失败 3 次后触发密钥吊销（见规则 8）。
- **计数器粒度**：按 `(发送端公钥, 本地会话 ID)` 粒度维护；连接重建则计数器重置；连续指中间无任何成功帧（详见 ADR-0002）。

### 规则 6：Replay-Enable=0 的安全约束（补丁 A，强制降级）

当 `PAL.Replay-Enable == 0` 时，Tuck 必须同时执行以下三条硬约束，缺一不可：

1. **风险降级**：无论 PAL.Risk-Level 原始值为何，Tuck 内部决策时强制视为 MEDIUM（等级 1）。这意味着永远无法触发 CATASTROPHIC 硬覆盖，从根本上杜绝利用重放发动高危物理攻击。
2. **强化验证**：必须强制通过 PAH-Signature 第一层验证（规则 5）。用防伪强度弥补防重放缺失，若签名验证失败，直接拒绝帧。
3. **审计强制标记**：审计日志必须显式记录 `"REPLAY_DISABLED"` 事件，且该条日志必须附带当前硬件时钟（软件阶段使用 CLOCK_REALTIME + 单调计数器合成，防回滚标记，详见 ADR-0007）。

**代码级约束**：

```rust
if pal.replay_enable() == 0 {
    // 强制降级，不可绕过
    let effective_risk = RiskLevel::MEDIUM;
    if !verify_pah_signature_64(&pal) {
        return Decision::Reject;
    }
    write_audit("REPLAY_DISABLED", effective_risk, hardware_clock());
    // 后续决策仅使用 effective_risk，丢弃原始高优先级
}
```

**调试模式例外（CI144_DEBUG=1）**：

- 仅当启动时环境变量 `CI144_DEBUG=1` 时，允许跳过规则 6 的风险降级（约束 1），但约束 2（强制 PAH 验证）和约束 3（审计标记）仍然生效。
- 环境变量仅在启动时读取，不可运行时动态切换（与物理拨码开关原则一致）。
- **规则 1-3（CATASTROPHIC 硬覆盖/审计/不可协商性）在调试模式下仍然生效**，不可绕过。
- 启动时必须输出明显警告：`WARNING: CI144 DEBUG MODE ENABLED — Replay-Enable=0 downgrade bypassed. DO NOT USE IN PRODUCTION.`
- 调试模式下 Replay-Enable=0 的帧，审计日志中额外标记 `DEBUG_MODE=1`。
- 默认值 Replay-Enable=1（强制检查），只有明确授权的场景才能设为 0。

### 规则 7：密钥轮换流程（补丁 C，16-bit 回绕触发）

**触发条件**：发送端（Helix-Mind）检测到 Seq-Counter 即将溢出（≥ 65534）时，必须在下一帧触发密钥轮换。预留 2 帧缓冲。

**轮换流程**：

1. 发送端生成新的会话加密密钥（AES-GCM 新 Key）。
2. 发送端发送一个特殊的 `KEY_ROTATION` 控制帧（非 PAL 数据帧），携带新密钥（由主密钥加密保护，AES-256-GCM）+ nonce（防重放）。
3. 接收端（Tuck）确认新密钥后，重置该源 ID 的 Last-Seen-Seq 缓存（允许新序列号从 0 开始）。
4. 若接收端未收到轮换帧而检测到序列号回绕（突然从 65535 跳到 0），直接视为异常重放攻击，立即拒绝所有帧并触发硬件告警，直到人工复位。

**帧类型分配**：KEY_ROTATION 为 BIND-19 新帧类型（建议 Type=0x07，需在 v2.0-alpha.1 前完成 BIND-19 v1.0 类型分配表逆向检查；若冲突则重新分配，备用 0x0F，详见 ADR-0008）。

**ACK 超时处理（修正项-01，fail-closed）**：

- 发送轮换帧后，等待接收端 ACK，超时时间 100ms，重试最多 3 次。
- 若 3 次全部失败，发送端必须：
  1. 触发硬告警（ERROR 电平 + 声光指示）；
  2. 停止发送所有数据帧，进入"密钥轮换失败"安全状态；
  3. 等待人工物理复位或带外管理干预后方可恢复。
- **严禁回退至旧密钥并继续发送数据帧**（状态不一致比停止服务更危险）。

**轮换期间帧处理**：等待 ACK 确认再切换密钥；期间数据帧仍用旧密钥，避免丢包（详见 ADR-0005）。

### 规则 8：密钥吊销流程（第二层验证触发）

- **触发者**：Anaphase（编排中枢）发起密钥吊销。
- **触发条件**：同一会话连续 3 次第二层 512-bit 验证失败（计数器粒度见规则 5 / ADR-0008）。
- **传播方式**：通过 BIND-19 控制帧广播至所有 Tuck。
- **生效时间**：尽力 ≤1 秒；超时未达则降级为 PAL CATASTROPHIC 硬覆盖紧急阻断（兜底，详见 ADR-0003）。
- **吊销后处理**：被吊销密钥的所有帧立即拒绝；需通过带外管理通道重新分发密钥后方可恢复。

## 七、CAPABILITY-13 物理 Scope 扩展

| Scope 名称 | 说明 | 关联 Risk-Level |
|---|---|---|
| `phys:low_speed` | 允许低速/低扭矩动作 | MEDIUM 及以下 |
| `phys:high_speed` | 允许高速/高扭矩动作 | CRITICAL 及以上 |
| `phys:override` | 允许触发 HARD_OVERRIDE | **仅 CATASTROPHIC，必须经人类授权或 HSM 签名** |
| `phys:human_call` | 允许并行呼叫人类协助 | 任何 Risk |

**phys:override 约束**：phys:override scope 不得由 AI 自主声明，必须由外部人类操作员授权或硬件安全模块（HSM）签发，Tuck 验证签名。

**帧中 CAPABILITY-13 携带的 Scope 列表必须与 PAL 中的 Risk-Level 匹配**。若 Scope 不足但 Risk-Level 过高，该帧在协议层面即视为非法。

## 九、Alpha 实现期间 ADR 待办清单（9 项，不阻塞 Alpha 启动）

以下 9 个实现细节已创建 ADR 占位符（ADR-0001~0030），在 v2.0-alpha 编码过程中逐个锁定。每个 ADR 从 Draft 转为 Active 后，对应实现方可编码。

| # | ADR | 主题 | 已明确的约束 | 状态 |
|---|---|---|---|---|
| B-1 | **ADR-0001** | PAH 第二层签名位置（INTENT-7 载荷头部扩展） | `[512-bit Sig] + [Varint Payload-Len] + [Payload]` | Draft |
| B-2 | **ADR-0002** | 第二层验证失败计数器定义 | `(发送端公钥, 本地会话 ID)` 粒度；连接重建重置；连续指中间无成功帧 | Draft |
| B-3 | **ADR-0003** | 密钥吊销流程 | Anaphase 发起 + BIND-19 广播 + ≤1 秒尽力 + 超时降级 CATASTROPHIC 硬阻断 | Draft |

| - | **ADR-0009** | Seq-Counter 32-bit 扩展方案 | 含帧结构扩展（是否扩展 BIND-19 头至 10/12 字节）、向后兼容评估；Alpha 期间评估，不阻塞当前设计 | Draft |

### ADR 锁定顺序建议

1. **ADR-0004（KEY_ROTATION 帧格式）**：Alpha 编码前必须锁定，帧格式是编码基础
2. **ADR-0001（第二层签名位置）**：Alpha 编码前必须锁定，影响 INTENT-7 载荷结构
3. **ADR-0002（第二层验证失败计数器）**：Alpha 编码期间锁定
4. **ADR-0005（轮换期间帧处理）**：Alpha 编码期间锁定
5. **ADR-0008（帧类型冲突确认）**：Alpha 编码期间锁定
6. **ADR-0003（密钥吊销流程）**：Alpha 编码后期锁定，依赖 ADR-0002
7. **ADR-0007（硬件时钟模拟）**：Beta 阶段锁定
8. **ADR-0006（主密钥管理）**：Beta 阶段锁定，非本协议范围
9. **ADR-0009（32-bit 扩展）**：Beta 阶段评估，不阻塞当前设计

## 附录 D：当前实现边界（软件阶段 · 高并发多租户生产级约束）

本附录定义 v2.0 规范在**纯软件实现（Helix-Mind + 软件 Tuck）**下的强制实现项与未来硬件预留项。软件阶段必须满足**多租户、异步、高并发**的生产级要求。

### D.1 必须实现（软件阶段，强制，不降低安全保证）

| 协议特性 | 软件实现要求 | 高并发/多租户约束 |
|---|---|---|
| **PAL 24 字节解析** | 内存直接偏移读取（`[u8; 24]`） | 无锁读取，零拷贝 |
| **PAH 第一层 64-bit 验证** | ed25519 软件库实现，截断算法 = SHA-256 前 64 位 | Tuck 直接在当前线程验证（10-50μs）；Mind/Anaphase 用 `spawn_blocking`；验证延迟 ≤100μs |
| **Seq-Counter 防重放缓存** | 并发 LRU/分片缓存 | 按 `(Tenant-ID, Source-ID)` 分片，使用 `DashMap`；容量 ≥10 万条目；TTL 自动清理 |
| **CATASTROPHIC 硬覆盖** | `tokio::sync::Notify` 或专用广播通道 | 独立高优先级队列，避免被常规负载阻塞 |
| **第二层 512-bit 签名验证** | ed25519 异步验证 | `tokio::spawn_blocking` 不阻塞事件循环；失败计数按 `(Tenant-ID, Session-ID)` 隔离 |
| **Replay-Enable=0 强制降级** | 按规则 6 实现，强制 Risk-Level=MEDIUM | 调试模式例外（CI144_DEBUG=1，仅启动时读取，规则 1-3 仍生效） |
| **密钥轮换（规则 7）** | 16-bit 回绕触发，KEY_ROTATION 控制帧 | ACK 超时 3 次失败后停止发送数据帧 + 硬告警 + 安全状态（fail-closed） |
| **审计日志（CAS 模拟）** | 文件追加 + HMAC 链 | `tokio::fs` 异步写入；每条包含上一条哈希，链式防篡改；硬件时钟用 CLOCK_REALTIME + 单调计数器合成 + 防回滚 |
| **多租户隔离** | 每个租户独立会话状态、计数器、密钥 | 禁止跨租户共享缓存或密钥 |

### D.2 未来硬件预留（当前软件模拟，接口不变）

| 协议特性 | 当前软件实现 | 硬件阶段替换为 |
|---|---|---|
| **PAH 第一层 64-bit 验证** | ed25519 软件库（必须实现，不可跳过） | ASIC/FPGA 加速 ECC 验证，接口不变 |
| **物理拨码开关启用降级模式** | 环境变量 `CI144_SIM_HW_FAULT=1` 启动时读取 | GPIO 物理拨码或 HSM 寄存器 |
| **硬件中断触发 CATASTROPHIC** | `tokio::sync::Notify` 模拟 | PCIe MSI-X/GPIO 中断线 |
| **审计日志硬件时钟** | CLOCK_REALTIME + 单调计数器合成 + 防回滚 | 硬件 RTC + 安全计数器 |

### D.3 高并发实现约束清单

1. **无阻塞解析路径**：PAL 头部读取零系统调用、零锁、零内存分配。
2. **防重放缓存**：使用 `DashMap<(TenantId, SourceId), AtomicU16>`；每 60 秒清理过期条目。
3. **第一层签名验证**：Tuck 直接验证（10-50μs）；Mind/Anaphase 用有界通道（`mpsc::channel(1000)`）防止验证积压。
4. **第二层签名验证**：`tokio::spawn_blocking`，失败计数使用 `DashMap` + `AtomicU8`。
5. **审计写入**：`tokio::fs::append` 异步写入；HMAC 链计算在 `spawn_blocking` 中完成。
6. **CATASTROPHIC 高优通道**：独立 `unbounded_channel`，`select!` 优先处理。

### D.4 对规范正文的零修改承诺

附录 D **不修改**协议规范的任何字段、偏移、规则语义。PAL 头部、BIND-19 帧结构、所有规则（1~8）文本保持**完全不变**。附录 D 仅作为"当前实现者的工作说明书"。软件阶段所有安全机制（第一层签名验证、防重放降级、密钥轮换）均按规范实现，性能优化不影响安全语义。
